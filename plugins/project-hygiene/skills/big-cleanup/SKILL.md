# Большая чистка

Основная работа — **сокращение**, а не переписывание. Документация в проекте, где долго работал
агент, состоит по большей части из следов принятых решений: абзац с обоснованием оседает после
каждого обсуждения. Такой абзац тратит контекст на каждом запросе, а пригождается раз в год.

Целевое состояние описано в [эталоне](${CLAUDE_PLUGIN_ROOT}/standard.md). **Прочитай его целиком перед началом** —
без него критерии ниже не работают.

## Границы

Что скилл делает:

- правит `*.md`, XML-доки и комментарии;
- перекладывает файлы по папкам, если раскладка расходится с эталоном;
- запускает форматирование.

Чего не делает **никогда**:

- не правит логику кода;
- не пишет тесты (только предлагает их в отчёте и заводит пункт в бэклоге);
- не переименовывает типы и члены;
- не удаляет пункты бэклога, не отмеченные галочкой, без ответа пользователя.

## Фаза 0. Подготовка

1. Проверь, что рабочее дерево чистое. Если нет — останови работу и попроси закоммитить: чистка
   даёт большой diff, и смешивать его с незакоммиченным нельзя.
2. Найди настройки стиля. Их два источника, и они дополняют друг друга:

   | Источник | Где искать | Кто читает |
   |---|---|---|
   | ReSharper | `<решение>.sln.DotSettings` рядом с решением, плюс глобальные слои на машине | ReSharper в студии и `jb cleanupcode` |
   | EditorConfig | `.editorconfig` в решении либо выше по дереву | ReSharper, компилятор, сборка |

   Поиск `.editorconfig` идёт от файла вверх до корня файловой системы, ближайший выигрывает,
   `root = true` останавливает подъём. Каскад из нескольких файлов — штатная ситуация, а не повод
   спрашивать; выбирать между ними тоже не нужно.

   Ничего из этого не нашлось — **предупреди перед фазой 6 и дождись ответа**: форматирование
   применит умолчания, которые могут разойтись с тем, что у пользователя настроено в IDE.

   Файл `.sln.DotSettings` не в репозитории, а профиль настроен глобально — это работает, но
   только на этой машине. Скажи об этом один раз, не настаивая: перенос профиля в слой
   Solution team-shared решение пользователя, а не твоё.

3. Составь список документов: корневой `CLAUDE.md`, проектные `CLAUDE.md`, тематические `*.md`,
   `Glossary.md`, `BACKLOG.md`, `DECISIONS.md`.

## Фаза 1. Разбор отстойника

Делается **первым**, до всего остального, иначе накопленное перетечёт в следующий цикл.

Каждую строку `DECISIONS.md` прогони по маршрутизации из части 2 эталона: правило → тест →
комментарий → выбросить. К концу чистки файл должен быть пуст.

Пять строк про одно и то же означают недостающее правило — сформулируй его и покажи в отчёте.

## Фаза 2. Сбор по документации

Ничего не меняй. Только читай и складывай в отчёт.

По каждому абзацу — единственный вопрос: **применим ли он к ещё не написанному коду?**

| Форма | Исход |
|---|---|
| «Во всех таких случаях делай так», «никогда не делай эдак» | оставить |
| «Здесь сделано так, потому что тогда-то выяснилось» | удалить, предварительно проверив, не выводится ли из него правило |
| Пересказ кода, хронология, обоснование выбора, похвала решению | удалить |

Отдельно проверь:

- **Таблицы состава.** Строка на класс — свернуть в строку на папку или связную группу. Критерий
  отдельной строки: исчезни она, что-то станет непонятно.
- **Термины.** Определение вне `Glossary.md` — удалить, оставив следствие, если оно есть.
- **Бэклог.** Отмеченные галочкой пункты вычистить, а то, что из них получилось, положить
  правилом в `CLAUDE.md` соответствующего слоя. Неотмеченные, но выглядящие сделанными — **в
  отчёт, вопросом**, не удалять молча.
- **Разделы по особенностям стека** (DI, заглушки для дизайнера и подобное). Не заводить и не
  удалять по эталону: есть — привести в порядок наравне с остальным, нет — не выдумывать.

## Фаза 3. Сбор по коду

Тоже без правок.

**Комментарии** — по категориям из части 5 эталона:

| Категория | Исход |
|---|---|
| Соответствует коду, описывает неочевидное | не трогать |
| Расходится с кодом | **в отчёт**: расхождение может значить, что ошибка в коде, а не в комментарии |
| Не несёт ничего, чего нет в самом коде | удалить |
| Защита от рефакторинга (костыль, осознанная неочевидность) | оставить |
| Объясняет, почему сделано так | маршрутизация из части 2 |

**XML-доки** — оставить только «что это». Обоснование внутри `<summary>` вырезать и прогнать по
той же маршрутизации.

**Раскладка папок** — сверить с частью 4 эталона. Предложения по переносу — в отчёт; сами переносы
делать в фазе 5.

## Фаза 4. Отчёт и утверждение

**Останов. Дальше без ответа пользователя не идти.**

В отчёт идёт интересное, а не всё: полный перечень удалённого есть в git.

| Показывать | Не показывать |
|---|---|
| Формулировки правил, выведенных из осадка | абзацы, удалённые по критерию без вариантов |
| Расхождения кода с комментарием — что из них правда | удалённый мусор |
| Комментарии, оставленные как защита от рефакторинга | форматирование |
| Предложенные тесты | |
| Пункты бэклога под вопросом | |
| Перекладывание файлов | |
| Всё, где ты сомневался | |

Дай сводку объёма: сколько абзацев уходит, из скольких файлов. Число нужно, чтобы пользователь
понимал масштаб, но перечислять их не нужно.

## Фаза 5. Смысловые правки

Применяй утверждённое. Порядок внутри фазы: документация, потом комментарии и XML-доки, потом
перекладывание файлов.

Отдельный коммит. Сообщение — по существу, без перечисления файлов.

## Фаза 6. Форматирование

Отдельным коммитом, чтобы механический шум не смешивался со смысловым diff.

### 1. Стиль кода

Стиль приводит **ReSharper CleanupCode** — тот же движок, что и Code Cleanup в студии, только из
консоли. Другие форматтеры не запускаются: два инструмента переписывали бы код друг за другом.

```
jb cleanupcode <путь к .sln>
```

| Параметр | Когда нужен |
|---|---|
| `--profile="<имя>"` | профиль отличается от того, что задан в настройках; имя — как в диалоге ReSharper |
| `--settings=<файл.DotSettings>` | нужно перебить все слои конкретным файлом |
| `--exclude=<маска>` | исключить папки, например сгенерированный код |
| `--verbosity=WARN` | вывод по умолчанию многословен |

Профиль отдельно указывать обычно не нужно. CleanupCode читает те же слои настроек, что и плагин
в студии: глобальные, `<решение>.sln.DotSettings` из слоя Solution team-shared, персональные.
Поэтому результат совпадает с тем, что даёт кнопка Cleanup у пользователя.

**Версия инструмента должна примерно совпадать с версией плагина.** Разъехавшиеся версии дают
разный результат на одном профиле, и тогда следующий запуск из студии переформатирует всё заново.
Заметил расхождение — скажи, но не обновляй ничего сам.

**Команда `jb` не найдена** — значит, консольные инструменты ReSharper не установлены: они
ставятся отдельно от плагина для студии. Посоветуй пользователю выполнить

```
dotnet tool install -g JetBrains.ReSharper.GlobalTools
```

и дождись ответа. Сам не устанавливай и не подменяй шаг другим форматтером: результат разойдётся
с профилем пользователя. Если ставить он не хочет — пропусти шаг, скажи об этом и переходи к
следующему; остальная чистка от этого не страдает.

### 2. Кодировка и переводы строк

Инструмент `llm-code-fixer:fix_files` — приводит файлы к UTF-8 с BOM и CRLF.

| Аргумент | Что передавать |
|---|---|
| `path` | **полный** путь к корню решения; обход рекурсивный |
| `filter` | регулярное выражение .NET по имени файла с расширением, без пути |
| `fixEncoding`, `fixLineEndings` | по умолчанию `true`, менять не нужно |

Фильтр для C#-решения:

```
\.(cs|xaml|axaml|csproj|props|targets|json|md|xml|resx|sln)$
```

Файлы, уже находящиеся в нужном виде, не перезаписываются, а похожие на бинарные пропускаются.
Поэтому запуск по всему решению безопасен и лишнего diff не даёт.

Шаг идёт **после** CleanupCode, а не до: тот перезаписывает файлы и может вернуть им LF или
сбросить BOM. Прогони наоборот — и приводить кодировку придётся ещё раз.

### 3. Проверка

Сборка должна проходить. Форматирование её ломать не должно, и если сломало — виновата
предыдущая фаза, а не эта.

## Частые ошибки

- **Переписывать вместо сокращения.** Хорошо сформулированный абзац с обоснованием — всё равно
  осадок. Красота изложения не спасает запись, не проходящую по критерию.
- **Выдумывать правило, чтобы не удалять.** Если из решения правило не выводится — оно удаляется.
  «Во всех таких случаях» с натяжкой хуже, чем ничего: оно будет применяться.
- **Тащить в отчёт всё подряд.** Отчёт, который нельзя прочитать, равен отсутствию отчёта, и
  утверждение становится формальностью.
- **Чинить код по ходу.** Увидел ошибку — в отчёт и в бэклог, а не в правку.
